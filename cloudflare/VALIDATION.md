# Shared-core validation — v3.1 development

Validated on 2026-10-25 using Node.js 24, Wrangler 4.152.0, real Docker images and
an actual Workers Free account. No plan upgrade was performed.

## One production business core

Both platforms import `shared/application.js`. Routes, group/node parsing,
subscriptions, share-key handling, language selection and the browser editor are
maintained once. Storage and cryptographic compatibility are platform adapters:

| Platform | Storage | Passwords | Limits |
| --- | --- | --- | --- |
| Docker | Existing data.json / users.json volume | Existing Werkzeug scrypt/PBKDF2; new compatible scrypt records | No Cloudflare Free data caps |
| Workers | D1 | Salted HMAC-SHA256 with independent AUTH_SECRET | Explicit Free CPU/input bounds |

The old Flask code is retained only as a compatibility fixture under `tests/legacy/`.
Production Docker uses Node.js 24 and contains no Python backend or npm runtime
dependencies. Shared templates/translations remain under `app/`.

## Real Docker upgrade / rollback

`tests/upgrade_docker.py` passed against both the original local Flask image and
the reproducible `tests/legacy/Dockerfile` fixture:

1. Start the old image, save real groups, share keys and a password into a volume.
2. Replace it with the Node image using the same volume and a different default
   password. The saved password still works; starting/reading rewrites no files.
3. Save groups/keys and change the password, then restart the new image.
4. Roll back to the old Python image, which reads the new files/password correctly.

Coverage includes scrypt, PBKDF2, Unicode passwords, additional accounts, unknown
JSON fields, file mode 0640 and uid/gid 1000, custom SHAREURL/BASEURL, 301 nodes,
a save larger than the Workers limit, a link longer than 4096 bytes and a long
Unicode group name. Docker needs no AUTH_SECRET. Standard port 8000, volume path
`/home/app/data` and documented environment variables remain compatible.

Node-generated password records were independently checked with real Werkzeug;
Node also verified scrypt (including custom parameters), PBKDF2-SHA256 and
PBKDF2-SHA512 records generated by Werkzeug. The self-hosted KDF is serialized to
avoid multiplying scrypt memory usage across concurrent requests.

The final local pass also covered two individually bind-mounted JSON files:
saving groups, changing a key and changing a password retained both host inodes,
and the old image could read the resulting files. Symbolic-link writes and
concurrent reads/writes passed adapter tests. The packaged image was rebuilt with
these compatibility fixes.

## Workers Free CPU regression after sharing the core

The shared-core HTTP workload completed 122 requests covering reads, writes,
password changes, revoked credentials, maximum supported data and rejection paths.
Tail returned **117 numeric CPU samples, all 0–8 ms**, with execution outcome `ok`.
The missing five tail samples are not presented as measured requests.

Per-case evidence: [CPU_RESULTS.csv](CPU_RESULTS.csv), sanitized to contain no
credentials, account identifiers or request URLs. Representative measurements:

| Workload | CPU |
| --- | --- |
| Repeated editor API | 0–5 ms |
| Repeated editor page | 1–3 ms |
| Repeated subscription | 1–7 ms |
| Password change / restore | 2–5 ms |
| Save 256 short nodes in 32 groups | 4 ms |
| Save exactly 16 KiB | 2 ms |
| Wrong/revoked password and rejection paths | at most 8 ms |

These are actual Workers `cpuTime` measurements, not client response latency.
Finite measurements do not prove an absolute bound for every future platform
condition or load. Daily Workers/D1 Free quotas still apply.

### How the Free target stays bounded

- No PBKDF2 or other slow password derivation is executed in Workers, including
  migration. Legacy development password rows require an offline reset/migration.
- AUTH_SECRET is an independent random 256-bit key, stored only in Worker secrets.
  D1 stores salted verifiers. D1 alone does not permit offline guesses; simultaneous
  loss of the key and D1 permits cheaper guesses than a slow password hash.
- Only completed immutable CryptoKeys are reused. Authentication results are not
  cached: each request checks the current D1 user record.
- Editor HTML is built ahead of time; the browser loads authenticated JSON and
  renders node controls. Data is escaped before insertion, and save controls stay
  disabled until loading succeeds.
- Authentication/data reads share a D1 query; subscriptions select only their
  requested group. Schema setup occurs during deployment, outside HTTP requests.
- Comment removal is a linear scan, including many unmatched comment openers.
- Workers supports 16 KiB save bodies, at most 64 stream chunks, 32 groups, 256
  nodes, 4096 UTF-8 bytes per link and 32 KiB processed settings records. Password,
  name, key and header processing have explicit bounds. Oversize input is rejected.
  **These Free restrictions are not applied to the Docker adapter.**

Earlier experiments with PBKDF2, successful-authentication caching and larger
payload bounds had over-10ms outliers. Those stages are not counted as passing
measurements. The production pprof API returned `No recent executions were found`
despite traffic; CPU conclusions are based on Workers tail, not a flamegraph.

## Latest local-only completion pass

The final completion pass made no public deployment and did not use account
credentials. A separate temporary Wrangler configuration used a dummy database
UUID, local SQLite, new test secrets, an invalid placeholder API token, disabled
telemetry, and an outbound proxy that refused external connections. The simulator
listened only on `127.0.0.1`. Its optional `Request.cf` metadata fetch was blocked;
the application does not rely on that metadata.

Full HTTP acceptance, all Free input/rejection boundaries, restart persistence,
and both missing-secret 503 guards passed locally. All simulator processes were
stopped afterward. These are functional checks; local elapsed times are not new
production CPU measurements. The CPU CSV above is retained from the earlier
shared-core cloud run.

## Local Free / Paid policy switching

`WORKERS_MODE` now defaults to `free`; `paid` selects a larger, still bounded
capacity policy. It never changes the account billing plan. The original cloud
CPU samples above apply to the Free policy, not the larger Paid limits.

An isolated local workerd/D1 regression passed Free → Paid → Free switching with
the same database and AUTH_SECRET, including a password changed through the web
API and a share key. Paid accepted 40 groups / 400 nodes, exceeding Free body and
record limits. An accidental downgrade returned 413, and switching back restored
all data without loss. Reducing the data under Paid allowed a successful return
to Free. Oversize bodies for both policies and an invalid-mode 503 were checked.
This test uses dummy credentials, loopback listeners and blocked outbound proxy
settings; it is available as `python3 scripts/workers_modes_local.py` and in CI.

The deployment entry now uses the repository root so the Deploy button includes
shared code. A clean temporary template installed dependencies from the local npm
cache, built the pages, passed Wrangler dry-run, and initialized local D1. This
checks local packaging; the hosted cloning wizard remains unverified. Secrets
examples and CI commands now use the same repository root as Wrangler config.
The clean root entry passed local HTTP acceptance and all Free boundary checks.
The rebuilt Docker image passed legacy scrypt/PBKDF2 upgrades, restart, rollback
and individual bind-mounted-file compatibility checks after these changes.
